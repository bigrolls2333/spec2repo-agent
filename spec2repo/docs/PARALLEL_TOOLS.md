# 按依赖执行并行工具

Agent 可以在一次模型响应中提出最多 8 个工具调用，平台同时执行最多 4 个互不冲突的调用。该设计减少逐个调用工具所需的模型往返，同时保留文件一致性、租约校验和预算约束。

## 调度规则

平台先校验整组工具名称、参数、调用 ID、依赖和控制操作位置，再执行任何工具。模型可在工具参数中使用 `depends_on`，引用本次响应中前面调用的 **1 起始序号**。例如第 3 个调用的 `depends_on: [1, 2]` 要求前两个调用成功。只允许向前引用，因此不会产生循环依赖；重复调用 ID、自依赖、向后依赖会在执行前被拒绝。

显式依赖只能增加约束，不能关闭平台推断出的冲突：

| 操作关系 | 执行规则 |
|---|---|
| 独立文件读写 | 无冲突时并行，最多 4 个 |
| 同文件写后读、读后写或写后写 | 按模型给出的调用顺序执行 |
| 文件路径祖先/后代关系 | 串行，例如写 `a` 和写 `a/b` |
| 目录枚举、全局搜索与写文件 | 保守串行，避免观察到不一致的目录状态 |
| 多个只读操作 | 可并行 |
| 终端命令、内部计划修订 | 全局串行边界，等待前序调用，后序调用等待它 |
| finish | 必须是最后一个调用，并等待全部前序操作成功 |
| propose_plan、request_clarification | 必须单独提出，避免持久状态切换后还执行其他工具 |

平台规范化文件路径并解析现有路径别名，对硬链接采用保守串行策略。每轮调度重新计算冲突，避免前序终端命令创建路径别名后沿用过时判断。终端命令可以操作整个工作区，因此不试图从 shell 字符串猜测精确读写集合。

例如一次响应包含“写 app.py、写 test_app.py、运行 pytest、finish”，前两个写入可并行，测试等待写入完成，finish 等待测试成功。如果测试失败，finish 得到跳过结果，模型下一轮读取反馈后修复。

调度器无法推断任意业务语义。如果某个调用的参数必须根据另一个调用的未知输出构造，模型需要等到下一轮再提出该调用；`depends_on` 只约束顺序和成功条件，不会自动把结果插入后续参数。

## 失败、上下文和持久状态

普通工具失败会返回有界反馈，依赖它的调用被跳过，独立分支仍可执行。每组响应按原始顺序生成一条 assistant 消息和全部对应 tool 结果，跳过的调用也有结果，不因并行完成顺序改变协议配对。

上下文裁剪以“整条 assistant 响应及其全部结果”为单位，避免保留一半工具交互。控制操作成功结束当前阶段时，由持久状态和下一阶段上下文接续；完整模型对话仍不是恢复依据。

租约丢失、基础设施错误等异常仍使本次执行失败或停止，不把它们当成普通业务反馈继续提交。独立操作没有跨工具事务：某个调用失败时，其他调用可能已经写入文件；模型需要结合工作区和反馈修复。只有完整提交的快照进入后续独立验收。

## 容器和预算

同轮并行工具各自使用 UUID 后缀的容器名，共享本次 attempt 的工作目录。每个容器保留 run、generation 和 tool 标签。工具完成时只清理自己的容器；恢复或取消时按 run/generation 标签清理该代次全部工具容器，避免同代次工具互相删除。

原有容器网络、权限和资源限制保留。单工具容器仍为 1 CPU、256 MiB；单 Agent 最多 4 个并行工具，因此瞬时资源开销会比串行模式更高。多 Worker 还会进一步叠加，部署时需要据主机资源控制 Worker 数量。

任务总预算没有放宽。每次模型调用仍先预留请求额度和 150 秒，涵盖模型与首轮工具；后续每轮工具执行前额外预留 30 秒，不增加模型调用次数。额外预留写入 MySQL 并受原有租约和总时间额度检查约束。
