# 小型上下文 token 对照实验（2026-10-26）

这次没有观察到 memory 配置降低总 token：baseline 两次合计 82,742，memory 两次合计 92,287，增加约 11.5%。两组成功率不同且样本很少，不能据此推断一般性的成本效果。

## 条件与原始证据

使用 deepseek-flash / api.deepseek.com，固定笔记 API 规格，串行 ABBA 顺序：baseline、memory、memory、baseline。每组重复两次，均采用 32 次模型调用、240,000 保守 token 预留、1800 秒预留上限，单次输出上限 4096；停滞干预关闭。实际 usage 与预算预留分开统计。

真实执行走 MySQL、Redis、Docker 与独立 HTTP 验收；计划自动批准，仅用于合成实验。原始模型用量来自供应商 usage，30/30 次调用均有记录。价格没有配置，费用未知。

## 解释边界

1. memory 两次均未调用 `update_task_memory` 或 `read_tool_output`。平台自动生成工具观察并注入上下文，但本实验没有检验主动笔记和证据分页的收益。
2. baseline 本身也有历史裁剪与近期操作摘要，因此这里比较的是新增记忆/短预览配置，不是“完全不做上下文管理”与完整配置的差异。
3. 两组各 15 次调用，总输入用量不同，说明不能简单用轮次数解释差异；工具定义、提示词、注入观察、具体生成路径都可能贡献差异。本次没有固定同一执行轨迹，无法归因到单个机制。
4. 基线两次因协议校验失败，记忆一次因预算失败，缺少同等成功交付质量的样本。不能把提前失败时的低用量当作节省。
5. 每组只有两次、一个公开短任务。不能声称显著改善成功率、稳定节省 token 或长任务一定更省。

目前可写的结论是：实现支持上下文容量控制、结构化记忆和证据检索；本轮没有证明 token 节省。简历不增加节省百分比。

下一步如需隔离机制效果，可先对相同工具轨迹比较上下文输入，再使用能触发长输出检索与跨阶段记忆的任务进行配对实验。前者只能检验输入体积，不能替代真实模型效果评估。本轮不继续追加付费任务。

## 复现入口

`scripts/evaluate_agent.py` 新增 `--cases` 与 `--profiles`，可选择小规模矩阵。已验证两组两次生成 ABBA 共 4 任务，原默认仍为 12 任务；Ruff 检查通过。

```powershell
.venv/Scripts/python.exe scripts/evaluate_agent.py --cases notes --profiles baseline memory --repeats 2 --output docs/experiments/context-small-plan-new.json
```

该命令只生成计划；真实执行需显式增加 `--execute --model-env <配置文件>`，输出文件不能已存在。
