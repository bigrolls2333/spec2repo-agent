# 任务提交接口并发测试

本机测试环境中，单 Uvicorn 进程在 32 并发下完成 4,628 次任务提交，三轮汇总吞吐为 **152.4 请求/秒，P95 283.1 ms，错误率 0%**。该结果衡量任务接入和事务落库能力，不表示模型生成吞吐或完整任务完成速度。

原始证据：[逐请求延迟与运行结果](experiments/benchmark-784a3fd26f844d8abe28b4464eaef6dd.json)。复现程序：[benchmark_api.py](../scripts/benchmark_api.py)。测试日期：2026-10-23。

## 测试口径

请求经过真实 TCP/HTTP、API Key 鉴权、CoreSpec 校验、规格指纹计算、MySQL 事务与响应序列化。每个正式测量请求使用新的幂等键，事务保存任务、幂等记录、创建事件和 Outbox，然后返回 HTTP 202。

使用同一份 [笔记 API 规格](../examples/notes_api.spec.json)，先发送 100 次预热请求，再按 8、32、64 并发顺序测量，重复三轮。每轮持续发起请求 10 秒，停止发起后等待在途请求结束，实际总耗时作为吞吐分母。每个客户端协程收到响应后才发下一次请求，属于固定并发的闭环负载；不自动重试。

吞吐量为成功请求总数除以三轮实际总耗时；延迟从客户端发出请求前计时，到收完响应结束。P50/P95/P99 对同档三轮的全部原始延迟合并后取 nearest-rank 分位数，不平均各轮分位数。该方法不衡量开放到达流量下的排队延迟，也不代表长时间稳定性或生产容量上限。

## 环境

| 项目 | 配置 |
|---|---|
| 操作系统 / Python | Windows 11 / Python 3.13.5 |
| 主机逻辑 CPU | 16；未采集 CPU 型号、内存容量及 Docker VM 资源配额 |
| API | Uvicorn 单进程，关闭访问日志；现有同步数据库处理路径 |
| 数据库 | Docker MySQL 8.4.11，专用 spec2repo_test 库 |
| 连接池 | 常驻 5，额外连接最多 5，等待超时 10 秒 |
| MySQL 参数 | innodb_flush_log_at_trx_commit=1，sync_binlog=1 |
| 数据目录 | compose.test.yaml 配置的 tmpfs，属于内存文件系统 |
| 客户端 | 同机 httpx asyncio，最多 64 条连接，单请求超时 15 秒 |
| 下游 | Relay、消费 Worker、模型、沙箱不参与测量；Redis 测试服务启动但不进入请求链路 |

**内存文件系统不能代表生产磁盘的持久化性能。** 本结果只能称为本机测试环境实测；同机负载发生器、固定规格、短测量窗口和逐渐增长的数据量也会影响数字。测试没有修改生产实现或扩大连接池，没有通过模拟数据库获得结果。

## 汇总结果

| 并发请求数 | 三轮请求总数 | 成功请求/秒 | P50 | P95 | P99 | 错误率 |
|---:|---:|---:|---:|---:|---:|---:|
| 8 | 4,457 | 148.0 | 48.2 ms | 95.4 ms | 126.2 ms | 0% |
| 32 | 4,628 | 152.4 | 204.3 ms | 283.1 ms | 333.1 ms | 0% |
| 64 | 4,493 | 146.2 | 364.4 ms | 1,183.9 ms | 1,934.3 ms | 0% |

随后独立补测 128 并发，仍为三轮各持续发起请求 10 秒，连接池上限相应增加到 128，避免把客户端 64 条连接的限制误认为服务端并发上限。服务端配置保持不变。结果如下，原始数据见 [128 并发报告](experiments/benchmark-1e563e175c334b46a41fe799ef3eaf5a.json)。这里的客户端连接池与服务端数据库连接池是两回事，后者仍最多 10 条连接。

| 并发请求数 | 三轮请求总数 | 成功请求/秒 | P50 | P95 | P99 | 错误率 |
|---:|---:|---:|---:|---:|---:|---:|
| 128 | 2,442 | 62.2 | 1,312.5 ms | 5,156.5 ms | 6,637.1 ms | 0% |

128 并发各轮吞吐为 55.8、72.0、58.0 请求/秒，落库数量检查通过。它是另一次进程启动后的独立短测，不是与前面三档交错进行的控制实验。吞吐下降和延迟上升说明这一负载下表现恶化，但没有剖析证据能把原因唯一定位到服务端；同机客户端竞争也可能影响结果。

三轮每档吞吐范围分别为 146.2～151.5、151.3～154.1、145.6～146.6 请求/秒。全部正式测量共 13,578 次，均返回 202，没有 HTTP 错误或传输异常。

32 到 64 并发没有带来吞吐增长，尾延迟明显增加。现象符合处理能力趋于饱和、请求等待增加的表现；尚不能仅凭这些结果把瓶颈归因于连接池、Python、数据库或客户端中的某一项。下一次性能优化应先采集 CPU、连接池等待和 SQL 耗时，再改变单个配置做对照。

## 正确性检查

正式请求、100 次预热以及额外的同键并发测试最终产生 13,679 个独立任务。按本次随机测试身份查询，runs、idempotency_keys、outbox、run_events 四张表均为 13,679 条，与预期一致。

额外 64 个并发请求使用相同幂等键和内容：全部返回 202，响应指向同一个 run_id，63 次标为幂等重放，数据库只有一条对应幂等记录。该检查验证并发提交不会重复创建任务；不据此宣称模型执行恰好一次。

## 复现

前提：已安装项目开发依赖、Docker Desktop 可用、已有 .env.test 测试配置。从 spec2repo 目录执行：

```powershell
docker compose --env-file .env.test -f compose.test.yaml up -d --wait
.venv/Scripts/python.exe scripts/benchmark_api.py
docker compose --env-file .env.test -f compose.test.yaml stop
```

单独补测 128 并发时，将中间命令换成 `.venv/Scripts/python.exe scripts/benchmark_api.py --concurrency 128`。参数只接受 1～128 并发，每个指定档位仍测三轮。

脚本只接受本机 spec2repo_test 数据库，先应用迁移，再启动绑定 127.0.0.1 随机端口的独立 API 进程，使用随机身份和临时密钥，结束后关闭该进程。不要与完整测试套件并行执行，因为套件会清理业务表。脚本保留本次测试记录，不清空数据库；重复运行会改变数据规模。原始 JSON 写入 docs/experiments，API 日志写入被忽略的 .runtime/benchmarks。测试不调用模型、不读取原项目模型密钥。

本次程序成功退出，报告 counts_match=true；静态检查输出 All checks passed!。测试服务在完成后已停止。

## 简历与面试表述

建议第三点：

> 基于 **FastAPI、MySQL 与 Redis Streams** 构建异步 Agent 任务服务，通过**事务 Outbox 与请求幂等**保障任务可靠入队、避免重复创建；本机测试环境下，单进程任务提交接口在 **32 并发**时实测 **152 请求/秒、P95 283 ms**，累计 **1.35 万次提交无请求失败**。

数字对应上面的 13,578 次正式请求，取保守简写“1.35 万次”。Redis 属于服务架构，152 请求/秒只覆盖 HTTP 到 MySQL/Outbox 的路径。面试时主动说明测试 MySQL 使用 tmpfs，并区分“接收任务”和“完成任务”。HTTP 吞吐用 RPS 更准确；若口头称 QPS，要明确指接口请求数，不是数据库 SQL 数。

口述回答：

> 我把接入层和 Agent 执行层分开测试，因为模型任务可能运行很久，不能把提交接口的吞吐当成生成能力。接入层收到请求后，会先在一个数据库事务里保存任务和 Outbox，提交成功再返回 202。我用真实 HTTP 和 MySQL 做了 8、32、64 并发的三轮短测。32 并发时汇总约 152 请求每秒，95% 的请求在 283 毫秒内返回；64 并发没有提升吞吐，反而明显增加了尾延迟，所以我没有用最大并发数包装性能。除了响应成功，我还核对了任务和 Outbox 的数量，并用 64 个同键请求验证只创建一个任务。这是本机内存文件系统测试库下的接入层结果，生产磁盘容量要用目标部署环境再测。
