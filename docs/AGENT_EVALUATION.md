# Agent 轨迹评估与停滞干预

2026-10-26 已完成四任务真实上下文对照：结果及限制见 [小型 token 实验](CONTEXT_TOKEN_EXPERIMENT.md)。本轮未证明 token 节省。

本模块让你沿模型调用、工具证据和验收结果定位失败，并比较 Harness 改动对交付质量的影响。默认 Agent 启用 `guarded` 策略；评测支持 `baseline`、`memory`、`guarded` 三组，只有显式执行实验才会调用真实模型。

## 停滞检测的依据

每个工具执行波次前后，对工作区文件内容计算有界指纹。扫描上限为 1000 个目录/文件条目、16 MiB 文件内容；排除 `__pycache__` 和 `.pytest_cache`，避免测试缓存变化掩盖重复失败。遇到链接、特殊文件、配额超限或无法稳定读取时，返回未知并清空检测历史，不把未知当作“没有变化”。指纹仅服务于启发式检测，不替代成果快照。

在最近 24 条被监测操作中，对比工具名、规范化参数、工作区指纹、成功状态、退出码和已捕获输出摘要。跨 3 个不同模型轮次重复同一结果，且工作区没有变化时，向下一轮上下文加入证据编号和重新审视方案的提示。同一轮批量重复调用只计一次。

| 情况 | 处理 |
|---|---|
| 相同终端失败跨 3 轮出现 | 提醒检查证据、补充信息或调整计划 |
| 相同终端失败跨 5 轮出现 | 抛出 `AgentStalled`，Worker 持久化失败状态并 ACK |
| 重复读取、搜索或列目录 | 给出提醒，不直接停止 |
| 工作区内容变化 | 清空重复计数和工具停滞提示 |
| 终端成功 | 清空重复计数和工具停滞提示 |
| 连续两次正式验收有共同失败项 | 在修复开始时提示重新审视方案，不追加预算、不自动判定根因相同 |

平台不替模型决定怎么修复；模型可以读证据、补充检索、修改实现或修订计划。状态变化和最终通过仍由原有业务状态机与独立验收控制。

检测历史只属于当前执行 attempt，恢复后重新统计；审计事件持续保存在数据库。首版采用精确证据匹配，带动态耗时或时间戳的错误输出可能不匹配，不能声称检测了所有语义死循环。忽略缓存目录也可能漏掉依赖缓存的进展，因此这里是有边界的启发式干预，而非无进展的数学证明。

## 如何关联轨迹

关联键为 `(run_id, generation, call, tool_call_id)`；不同模型轮次可能复用 provider 的工具 ID，不能只凭 tool_call_id 全局查找。

- `agent.trace_started`：策略、阶段、规格指纹、提示词和工具定义哈希、模型标识、初始快照。
- `agent.tool_batch`：工具 ID 与依赖索引；`tool_wave` 记录实际波次。
- `agent.tool_requested/returned`：参数哈希、输出哈希、证据 ID、耗时和退出码。
- `agent.tool_observed`：波次前后的工作区指纹与输出摘要，用于跨策略计算重复操作。
- `agent.tool_skipped/failed`：依赖失败跳过或工具基础设施异常。
- `agent.progress_intervention`：触发依据、证据引用与提醒/停止动作。
- 原有提交、验收事件和报告通过任务、代次及快照关联，控制工具的等待转换由这些业务事件说明。

轨迹不保存私有推理文本，也不把任意工具参数和供应商异常正文写入事件。输出证据沿用任务隔离、有界存储与有限脱敏。模型错误分类使用可观测事实：HTTP 状态、传输失败、响应协议、工具封装、批次校验、明确的输出上限和截止时间。只有 provider 返回 `finish_reason=length` 才归为输出上限，不根据残缺 JSON 猜测。

## 三组对照比较什么

| 策略 | 模型可用能力 | 共同条件 |
|---|---|---|
| baseline | 原有近期交互和操作摘要，工具输出最多 8000 字符；无任务记忆/输出检索工具 | 相同执行器、隔离、预算和独立验收 |
| memory | 加入结构化记忆、短预览与证据分页 | 同上 |
| guarded | memory 加停滞干预及重复验收失败提示 | 同上 |

三组均记录输出证据和工作区指纹，以便使用相同观测口径；baseline 是本版本的消融配置，不是旧 Git 版本的完整复现。memory 与 baseline 同时改变了记忆和输出呈现，因此不能把差异全部归因于单个组件。

默认任务矩阵为笔记 API、任务 API 两个固定公开规格，3 个策略，各重复 2 次，共 12 个任务。每个任务独立运行，策略顺序轮换；统一模型、调用和时间预算以及输出上限。报告冻结规格文件与源码/实验脚本哈希，记录模型标识、provider 主机、镜像 ID 与实际验收套件哈希。两个公开任务不构成保留测试集，也不足以证明跨领域泛化。

## 运行入口

在 `spec2repo` 目录运行以下命令，仅生成实验计划，不读取模型密钥、不请求模型、不启动任务：

```powershell
.venv/Scripts/python.exe scripts/evaluate_agent.py --repeats 2 --output docs/experiments/evaluation-plan-20261025.json
```

输出路径必须是新文件，避免覆盖已有证据。`--help` 可查看完整参数。

真实执行入口是同一脚本的 `--execute --model-env <配置文件>`；它需要现有专用 MySQL/Redis、固定 Docker 镜像和模型配置，自动批准合成测试任务。单次允许 1～3 次重复，即 6～18 个真实任务，可能产生模型费用。本批没有执行付费对照。准备环境沿用 [Agent 运行说明](RUN_AGENT.md)，模型发送内容沿用 [实验说明](AGENT_BENCHMARK.md)。

## 指标如何解释

- 最终成功率：独立验收通过任务数 / 全部已启动任务数。
- 首次通过率：首次正式验收通过任务数 / 全部已启动任务数；生成阶段失败不会被排除。
- 修复成功率：首次验收 FAILED 后最终成功数 / 首次验收 FAILED 数。ERROR 属于验收基础设施问题，不进入修复分母。
- 重复失败/读取次数：工作区未改变时，相同参数与捕获输出跨轮次重复的可观测次数；不要求模型遵循固定工具顺序。
- 每成功任务 token：所有任务（包括失败）的实际 token 总和 / 成功任务数。任何调用缺失 usage 时该指标为空，另报已知 token 和覆盖调用数。
- 每成功任务耗时：所有任务完成耗时之和 / 成功任务数；不是单个成功任务的延迟，也不是持续负载吞吐。

报告按策略保留逐例结果；中途基础设施中断会保留部分结果并标记 `complete=false`，不同样本覆盖的均值不能直接比较。异常分类计数与失败任务状态分别列示，不能相加当作失败任务总数。没有价格配置时费用为未知。
