## 2. 规格契约与验收边界

本主题对应 [CoreSpec 实现](../src/spec2repo/domain/spec.py)、[任务管理规格](../examples/task_api.spec.json) 和 [规格测试](../tests/test_spec.py)。题目为本项目自拟；验收与过程评估的追问方式参考下文 S2。

### Q001｜如何区分四种“通过”？

- [ ] 能区分 JSON/规格结构有效、可以进入规划、人工批准和最终验收通过，并指出哪些已实现。
- 主问题：CLI 返回 valid=true、ready_for_planning=true，系统究竟确认了什么？
- 追问：如果业务需求本身相互矛盾，当前校验器一定能发现吗？当前是否已有审批服务和代码验收器？
- 证据定位：CoreSpec.ready_for_planning、cli.main，以及样例输出。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我把“通过”拆成四层：输入结构合法、信息足够进入规划、方案得到批准，以及生成结果通过独立验收。它们回答的是不同问题。比如规格里的字段和引用都合法，只说明系统能理解这份输入；关键业务问题还没回答，就不能直接开始规划。即使规划完成，也不能据此认定最终代码满足需求。

具体做法是把这四层落实成独立的状态和检查：输入层检查结构和引用，规划前检查阻塞问题，审批绑定确定的方案，最终由独立验收器判断代码行为。结构校验负责确定性的约束，业务歧义通过澄清解决。这样每一次状态推进都有明确依据，模型不能因为生成了一份看起来完整的结果，就自行宣布任务成功。

</details>

### Q002｜需求都有验收项，为什么仍不等于正确？

- [ ] 能举出“引用覆盖完整，但语义遗漏或验收过弱”的反例。
- 主问题：每条 Requirement 都被 AcceptanceCriterion 引用，为什么仍不能证明规格完整或生成代码正确？
- 追问：如果验收项只是“接口能调用”，会漏掉什么？当前描述性验收项和未来可执行验收用例如何对应？
- 证据定位：check_traceability 只检查引用和覆盖；示例中分页、状态迁移、持久化的行为描述。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

需求与验收项建立关联，主要解决可追溯性和显式遗漏的问题，但关联存在，不代表验收足够严格。比如“支持分页”只配一个“接口返回成功”的检查，虽然形式上覆盖了需求，却没有验证页大小、排序稳定性和边界参数。

所以我把验收分成两层：先用结构校验保证每条需求都有对应验收项，再用独立可执行测试检查正常、异常和边界行为。比如分页要检查页大小、顺序和非法参数，持久化要检查服务重启后的数据。评测还保留没有直接反馈给 agent 的输入变体，检验它是否满足业务规则，减少针对固定样例写特判的问题。

</details>

### Q009｜为什么需要稳定的需求 ID？

- [ ] 能解释 ID 如何连接需求、接口、实现任务与失败结果。
- 主问题：为什么不直接把完整需求文本复制到每个任务和测试里？
- 追问：重复 ID、引用不存在的需求、需求完全没有验收项，分别有什么后果？未来删除或拆分需求时，旧结果怎样保留可解释性？
- 证据定位：check_traceability；重复 ID、未知引用、无验收覆盖的测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

稳定的需求标识解决的是“这段实现或这个失败到底对应哪个要求”的问题。需求文本可能很长，也会修改；如果每处都复制一遍，容易出现不同副本不一致，而且失败结果难以追溯。

项目让接口和验收项引用需求标识，并拒绝重复标识、无效引用和没有验收项的需求。执行记录同时保存规格版本和内容快照，需求变化后，旧结果仍对应当时的要求。这样既能从失败测试追到具体需求，也能解释一次修改影响了哪些接口和验收项，避免需求文本在多个位置复制后逐渐不一致。

</details>

### Q010｜什么问题应该阻塞 agent？

- [ ] 能区分业务语义缺失与实现偏好，并解释当前判断的局限。
- 主问题：为什么未回答的关键业务问题需要阻塞，而模块如何命名通常不需要人工回答？
- 追问：blocking=false 的未回答问题会怎样？空白答案能否通过校验？当前代码会自动判断答案是否解决了业务问题吗？
- 证据定位：OpenQuestion、blocking_question_ids，以及阻塞/非阻塞问题测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我会看一个未决问题是否会改变外部可观察的业务行为。比如预约能否重叠、已完成任务能否取消，会影响接口契约和验收标准，需要先澄清；模块命名、内部函数组织等实现选择，一般可以由 agent 自主决定。

规格里显式区分阻塞和非阻塞问题：阻塞问题没有解决就进入等待，非阻塞问题不必打断执行。澄清的目的不是简单填一段回答，而是把答案落实到业务规则和验收条件，再据此继续规划。这样把需要用户决定的业务语义和 agent 可以决定的实现细节分开，减少无意义的人工确认。

</details>

## 3. 项目定位、Agent 与工程边界

本主题对应 [改造计划](../IMPLEMENTATION_PLAN.md) 和现有代码目录。S1 提供模型与程序分工的面经参考，S2 提供框架取舍的参考；这里讨论已确定的设计，不把未来 agent loop 当作当前实现。

### Q005｜为什么从 Paper2Repo 改为 Spec2Repo？

- [ ] 能结合实际耦合说明改造原因，不只回答“更通用”。
- 主问题：旧项目中哪些概念可以复用，哪些地方仍然绑定模型、数据集、训练和损失函数？
- 追问：为什么没有直接重命名 PaperSpec？两个不同 API 业务案例能证明什么，又不能证明什么？
- 证据定位：计划中的迁移表与首版范围；当前 profile 固定为 python_api。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

原项目围绕论文复现组织输入，很多字段默认关联模型结构、数据集、训练和损失函数。我要解决的任务扩大到普通 API 项目后，直接改名字仍然会保留这些隐含假设，后续规划和验收也会被论文场景绑住。

因此我把通用部分抽成需求、接口、约束、待澄清问题和验收标准，把业务类型作为独立配置，保留“规划—实现—验证—修复”的执行思路。业务范围聚焦 Python API，用任务管理和预约管理这类不同业务检验同一条链路的复用。这样既去掉了论文专用假设，也控制住了运行环境和验收成本，能把精力放在 agent 自主实现和后端可靠性上。

</details>

### Q006｜模型和程序分别负责什么？

- [ ] 能解释自主性与执行边界如何同时存在。
- 主问题：在我们确定的架构中，哪些决定留给 agent，哪些必须由平台程序强制执行？
- 追问：从空工作区开始后，agent 可以改需求或降低验收标准吗？为什么固定 Python 环境不等于预先写好业务代码？
- 证据定位：计划中的空工作区、可修订计划、预算与验收边界。
- 来源：根据 [S1 的公开面经汇编](https://www.nowcoder.com/discuss/940040254214389760?sourceSSR=users) 改写，不是原题逐字转载。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我的划分是：模型负责需要推理和探索的工作，平台负责必须稳定执行的约束。比如模块怎么拆、用什么实现方式、读哪些文件、根据测试失败如何调整方案，可以交给 agent；身份权限、预算、执行隔离、状态提交和成功标准由程序控制。

这样既保留 agent 的自主性，也避免让模型自行宣布成功或降低验收要求。固定 Python 运行环境提供工具和依赖，业务代码由 agent 从空工作区完成。实现方案允许自主修订；涉及业务需求或接口契约的变更，则回到澄清和审批流程。我的重点是让模型在明确的任务目标内自主探索，同时让权限、成本和结果提交保持可控。

</details>

### Q007｜为什么先写 domain，再写 FastAPI？

- [ ] 能说明领域规则与输入输出适配层的职责。
- 主问题：为什么不把规格校验和状态迁移全部写进 HTTP 路由？
- 追问：CLI 与未来 API 如何复用规则？没有数据库时哪些行为能测，哪些不能测？如果更换编排框架，需要修改哪些部分？
- 证据定位：domain/spec.py、domain/lifecycle.py 与 cli.py 的调用关系。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我先把领域规则独立出来，是希望“什么输入合法、什么状态允许迁移”只有一份定义，不因入口不同而改变。HTTP 路由负责接收请求、认证和返回结果，CLI 负责命令行交互，它们都调用同一套规则，避免两边各写一份以后逐渐不一致。

这种分层也便于分开验证：没有数据库时，可以测试规格约束和状态规则；涉及并发提交和持久化，就必须到 repository 和真实数据库层验证。将来更换编排框架，优先替换调用和调度方式，而不是重写业务规则。代价是多了一层组织结构，所以我只按实际职责拆分，没有为所有类都增加抽象接口。

</details>

### Q008｜为什么不一次实现完整 agent 平台？

- [ ] 能解释阶段顺序、学习成本和范围取舍。
- 主问题：为什么先验证规格和状态规则，再引入持久化、消息队列和真实模型？
- 追问：哪些失败更适合用假执行器定位？什么情况下复用框架，什么情况下自研一小段运行时？本项目当前有没有证据证明自研比框架更好？
- 证据定位：计划中的 50 小时安排；第五阶段已接入模型适配器、工具循环与持久审批，真实效果见阶段实验记录。
- 来源：框架与自研取舍的提问方式参考 [S2 的个人面经](https://api-cdn.nowcoder.com/feed/main/detail/fa50ef5521f84cb788f911cd31e5a98a?sourceSSR=post)。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我采用分阶段推进，是为了把不同来源的不确定性分开。如果一开始同时接模型、队列、数据库和沙箱，任务失败时很难判断是需求理解错、模型输出错，还是消息和状态处理出错。先用确定性假 worker 验证后端，能稳定复现重复消息和提交失败，再逐步增加真实执行能力。

我把主要投入放在规格驱动、可靠提交、执行恢复和独立验收上，限制业务栈来降低联调成本。运行时选择保持轻量，是因为这样更容易明确状态、事务和失败恢复的责任；框架则优先复用成熟的模型接口和通用组件。判断是否引入更重的编排框架，主要看持久等待、工作流复杂度和维护成本，而不是为了自研而自研。

</details>

## 4. 任务状态、并发与取消

本主题对应 [生命周期实现](../src/spec2repo/domain/lifecycle.py) 与 [生命周期测试](../tests/test_lifecycle.py)。题目由代码与讨论中的竞态场景自拟；第二阶段验证数据库条件更新，第三阶段验证模拟消费并发，第四阶段补充执行租约与旧代次提交保护。

### Q003｜为什么 Python 版本检查不等于并发安全？

- [ ] 能画出两个请求读取同一版本后分别通过检查的交错时序。
- 主问题：两个请求同时读到 version=3，即使都检查 expected_version，为什么仍可能冲突？
- 追问：检查与写入分开会留下什么窗口？已实现的数据库更新还需要匹配什么，并检查什么返回结果？单进程锁能否解决多 worker 的问题？
- 证据定位：transition 是纯函数；RunRepository.change_status 使用数据库条件更新，test_repository.py 验证竞争失败者被拒绝；执行期间另由 ExecutionRepository.guard 校验租约与 generation。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

问题在于“检查”和“写入”如果分开，就存在并发窗口。两个请求可能都读到同一个版本，也都通过 Python 判断，然后分别写回，后一次覆盖前一次。单进程锁只能保护本进程，多个 API 或 worker 进程之间仍然会竞争。

项目把这个判断放进 MySQL 的同一条条件 UPDATE：只有任务状态和版本仍符合预期才允许更新，并检查影响行数。失败的一方重新读取状态，再决定是否继续，不能盲目重放旧操作。数据库更新用这种方式防止并发覆盖；长任务则结合租约和执行代次限制提交权限，每次尝试使用独立工作区，避免旧执行者覆盖新结果。

</details>

### Q011｜取消和成功同时发生，谁生效？

- [ ] 能分别解释取消先提交和成功先提交两条路径。
- 主问题：用户请求取消时，worker 恰好验证通过准备完成，系统应该如何决定最终状态？
- 追问：CANCELLING 为什么不能再转 SUCCEEDED？已经成功的任务为何不能伪装成取消成功？当前顺序测试为什么还不是数据库竞态测试？
- 证据定位：test_cancel_wins_then_completion_cannot_commit 与 test_completion_wins_then_cancel_is_rejected。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我让数据库中的原子状态提交决定结果，而不是根据两个请求各自的开始时间判断。如果成功先有效提交，任务已经结束，后来的取消返回冲突；如果取消先被接受，任务进入取消中，后来的成功提交必须被拒绝。

实现上先检查业务允许的状态迁移，再用状态和版本条件更新数据库，状态事件也一起提交。测试分别覆盖两种先后顺序，并在真实 MySQL 中让两个提交并发竞争，检查只有一个能生效。取消决定提交以后，执行端停止推进任务并清理所属资源；即使旧执行者稍后返回，也不能再把任务改成成功。

</details>

### Q012｜取消是一个状态，还是一段过程？

- [ ] 能区分排队任务与正在运行任务的取消行为。
- 主问题：为什么运行中的任务先进入 CANCELLING，而等待中的任务可以直接进入 CANCELLED？
- 追问：后续涉及哪些资源清理？为什么接受取消请求不等于外部模型已停止执行或不再计费？当前纯函数会终止任何进程吗？
- 证据定位：_ALLOWED 中等待态与运行态的差异；第四阶段运行中取消测试验证容器清理与完成提交被阻断。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

取消运行中任务是一段过程，因为除了更新数据库，还可能需要停止新工具调用、终止容器和处理临时产物。先进入“取消中”，表示取消决定已经生效；确认资源清理后再结束。排队或等待中的任务还没有实际执行，可以直接取消，迟到的队列通知再根据数据库状态忽略。

我把“取消决定生效”和“资源清理完成”分开处理：先阻止新工作和成功提交，再终止所属执行资源，最后记录取消完成。外部模型请求有自己的生命周期，本地停止等待不一定能撤销供应商已经开始的计算，因此调用记录和费用仍需要保留。这样取消状态能准确反映平台能控制的动作，也便于排查清理过程中的异常。

</details>

### Q013｜失败后重试与重复执行是一回事吗？

- [ ] 能解释允许 FAILED → QUEUED 不代表恢复机制已经完成。
- 主问题：为什么允许失败任务重新排队，但不允许成功或取消的任务直接重新排队？
- 追问：显式重试需要哪些新的执行记录？状态 version 与执行 generation 各自解决什么问题？为什么纯状态规则与执行权校验需要分层？
- 证据定位：RunSnapshot、FAILED 的允许迁移，以及第四阶段 Attempt/generation；人工重试 API 属于后续实施。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

显式重试表达的是一次新的业务执行决定，重复投递通常只是同一次决定在传输中又出现了一遍。前者需要重新检查条件并建立新的执行记录，后者应该去重，不能因为消息到达两次就创建两次有效工作。

一次显式重试会重新检查任务条件，并用 attempt 记录新尝试、用 generation 区分有效执行者；状态版本负责防止并发覆盖。这样既能保留历史失败原因，也能拒绝旧尝试迟到的提交。成功和已取消的任务不会被旧消息自动重新排队，用户希望重新生成时，需要发起明确的新任务。

</details>

## 5. 版本、指纹与数据约束

本主题对应 [规格模型](../src/spec2repo/domain/spec.py) 中的 fingerprint 和不可变字段设置，题目为本项目自拟。先解释当前行为，再讨论审批与版本演进，不要求背诵哈希算法内部实现。

### Q004｜规格版本与指纹为什么都需要？

- [ ] 能区分人工维护的业务版本与内容计算得到的指纹。
- 主问题：如果已经有 version，为什么还计算 SHA-256？如果已有 hash，为什么还保留 version？
- 追问：内容变了但版本忘记递增，当前能否仅凭一个输入发现？审批如何绑定内容？hash 能证明需求语义正确吗？
- 证据定位：version 字段、fingerprint，以及学习文档中的版本边界。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

版本号服务于人的理解和业务流程，内容指纹服务于程序的精确比较。版本可以表达“这是第几次修订”，但有人可能改了内容却忘记改版本；指纹能识别内容变化，但一串哈希值并不能表达这次修改的业务含义。

项目保留两者，并对规范化后的规格计算 SHA-256，用于幂等请求比较和审批内容绑定。审批通过的是一份确定内容，内容变更后需要重新判断审批是否有效。版本递增约定需要结合历史记录检查，需求是否合理则由澄清和验收判断；哈希承担的是内容一致性检查，职责比较明确。

</details>

### Q014｜为什么不同 JSON 格式得到相同指纹？

- [ ] 能解释模型规范化、键排序、编码与字段顺序的影响。
- 主问题：修改空白、缩进或对象键顺序，为何不应改变当前规格指纹？
- 追问：调换 requirements 数组顺序会怎样？把同一业务需求换一种中文表述会怎样？为什么它不属于语义去重？
- 证据定位：json.dumps 的配置和指纹测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

指纹的目标是比较系统接受的规格内容，不是比较文件排版。所以项目先解析并校验规格，再按固定方式序列化：对象键排序、统一编码、去掉无关格式差异。仅修改缩进、空白或对象键顺序，不应该被误判成新的请求内容。

数组顺序会保留，因此调换需求列表顺序可能改变指纹；换一种中文描述也会改变指纹。这是内容层面的精确比较，不是语义去重。这样的边界比较可预测，适合幂等冲突判断；如果需要判断两份需求语义相同，应作为单独能力评估，不能直接依赖哈希。

</details>

### Q015｜不可变模型到底保护了什么？

- [ ] 能解释 frozen 模型和 tuple 的作用，同时指出它们不提供分布式锁。
- 主问题：为什么规格使用 frozen 模型、集合使用 tuple？
- 追问：如果 frozen 模型里放一个可变 dict，嵌套内容是否自动获得同样保护？不可变对象是否意味着两个进程不能并发提交冲突结果？
- 证据定位：Contract.model_config 和集合字段；此题的嵌套 dict 是反例讨论，不是当前实现字段。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

不可变模型主要是减少进程内的意外修改：规格校验并计算指纹以后，不希望另一个函数又悄悄改动它，导致执行内容和记录不一致。因此项目限制字段重新赋值，集合也使用不可变序列。

不过这不是数据库锁，更不是分布式并发控制。即使每个进程里的对象都不可变，两个进程还是可能提交互相冲突的结果。另外，不可变模型中如果放可变字典，也不能自动保证嵌套内容完全不可变。不可变设计在应用内减少误改，跨进程的一致性仍由数据库事务和条件更新保障。

</details>

## 6. Python、校验与接口行为

本主题对应 [CLI](../src/spec2repo/cli.py)、[字段定义](../src/spec2repo/domain/spec.py) 与 [CLI 测试](../tests/test_cli.py)。题目由当前实现自拟，强调可观察行为和错误边界。

### Q016｜类型注解与运行时校验有什么区别？

- [ ] 能说明 Python 注解、Pydantic 校验与业务校验各自的职责。
- 主问题：为什么声明 version 是 int 后，仍然指定 strict 和范围约束？
- 追问：输入 true、字符串 "1"、0、负数分别会怎样？为什么 JSON 能被解析，不代表能构造合法 CoreSpec？
- 证据定位：version 定义与参数化测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

Python 类型注解主要帮助开发和静态检查，不会自动拦截所有外部输入。Pydantic 负责在运行时把输入变成符合约束的数据，业务校验再检查字段之间的关系，比如验收项引用的需求是否存在。

版本号这里使用严格整数和正数约束，是为了避免把布尔值或字符串自动当作版本接受。true、字符串形式的数字、零和负数都不符合契约。JSON 解析成功只说明语法成立，远不等于业务对象合法。我会把这些检查放在系统边界，避免无效输入进入数据库后才引起更难定位的问题。

</details>

### Q017｜为什么拒绝未知字段？

- [ ] 能举出未知字段被忽略导致业务错误的例子。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我选择拒绝未知字段，是为了尽早暴露契约不一致。对于规格驱动项目，用户可能以为某个限制已经传给系统，实际却因为字段拼错被静默忽略，这比明确报错更危险。严格校验能让这类问题在提交时就被发现。

### Q018｜为什么 CLI 需要三种退出码？

- [ ] 能解释输入错误与合法等待状态的区别。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我区分了三种结果：规格合法且可以继续、输入不合法、规格合法但需要澄清。它们对应不同的后续动作。如果把等待澄清也当成普通错误，上层脚本可能盲目重试，而实际需要的是用户补充信息。

- [ ] 能解释诊断信息与敏感数据暴露之间的取舍。
- 主问题：为什么格式校验失败时，不把完整规格输入直接写到错误输出？
- 追问：关闭 Pydantic errors 中的 input 是否等于实现了完整脱敏？如果用户在字段名或业务文本里嵌入凭证，还需要检查哪些输出路径？

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

错误信息应该帮助定位问题，但不应该默认复制完整输入。规格可能包含业务信息，甚至被误放入凭证，如果直接回显或写日志，就会把一次参数错误变成数据暴露。因此保留错误类型、必要位置等诊断信息，尽量不输出原始请求内容。

脱敏要沿整条链路考虑，包括校验错误、数据库异常、工具输出和第三方响应。我的原则是默认记录错误类别、位置和关联任务等诊断信息，只在受控场景提供必要上下文；同时用包含敏感内容的异常输入做回归测试。这样既保留排查问题的线索，也减少原始业务输入在日志中扩散。

</details>

## 10. 消息投递、去重与恢复（第三阶段新增）

### Q035｜为什么 Outbox 仍然会发重复消息？

- [ ] 能画出 XADD 成功、MySQL 标记失败的时序。
- 主问题：既然创建任务和 outbox 已在同一事务，为什么仍不能保证 Redis 只收到一次？
- 追问：先标记再发送有什么风险？发布结果超时但实际成功怎么办？Redis message ID 和 event_id 哪个适合业务去重？
- 证据定位：Relay.publish_one、test_publish_success_then_sql_rollback_can_republish。
- 来源：借鉴 [S3](https://www.nowcoder.com/feed/main/detail/1d2977971c444575b89313805d46b55d) 的消息幂等主题，结合本项目失败窗口改写。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

Outbox 把数据库内部的写入变成一个事务，但 Redis 发布不在这个事务里。比如 Redis 已经收到消息，应用还没把“已发布”写回 MySQL 就退出了，恢复后只能看到未发布记录，于是再次发送。这个重复是正常故障路径，不应该靠猜测上一次有没有成功来避免。

项目选择先确保不会因为这个窗口漏发，再让消费端幂等处理。同一个业务事件有稳定的事件标识，重发可以产生不同 Redis 消息 ID，但数据库只允许一份有效消费回执。已经通过发布后数据库失败的实验验证了这一点；这也说明不能用每次都会变化的消息 ID 作为业务去重依据。

</details>

### Q036｜为什么选 Streams 而不是 Pub/Sub？

- [ ] 能解释离线消费者、保留记录与消费确认的差异。
- 主问题：如果用 Redis Pub/Sub 发布任务，消费者断线期间的任务怎么办？Streams 提供哪些额外机制？
- 追问：Streams 有持久化就不需要 MySQL 对账了吗？同组两个消费者和两个不同消费组的行为有什么区别？
- 证据定位：Streams.ensure_group/read；消费组起点为 0-0；Stream 丢失实验。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

任务通知需要消费者离线后还能继续处理，而 Pub/Sub 更适合在线广播，订阅者断线时错过的消息不会为它保留。Streams 提供消息记录、消费组和未确认消息管理，适合这里的异步任务分发。

同一个消费组内，消费者共同分担新消息，但恢复时仍可能重复投递；不同组维护各自的消费进度，可以分别读取同一条消息。不过 Streams 也不是业务真相的唯一保存位置，消息可能因为数据丢失或误删而消失，所以项目仍从 MySQL 对账补投。这样选型是结合任务恢复要求，不是认为 Streams 在所有场景都优于 Pub/Sub。

</details>

### Q037｜为什么提交后才 ACK？

- [ ] 能逐步解释提交前失败和提交后 ACK 失败的不同结果。
- 主问题：如果先 ACK 再写消费回执，进程在两步之间退出会怎样？现在顺序相反又引入什么问题？
- 追问：回执和审计事件为什么必须一起提交？ACK 会删除 Stream 消息吗？如果 ACK 结果不确定，是否要撤销已提交的回执？
- 证据定位：SimulationWorker.handle；test_processing_rollback_leaves_pending_for_recovery、test_commit_before_ack_then_reclaim_is_idempotent；[XACK 官方语义](https://redis.io/docs/latest/commands/xack/)。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

如果先 ACK，再写数据库，进程在中间退出，队列已经认为处理完成，数据库却没有结果，这个工作可能就漏掉了。因此我先提交数据库中的消费回执和审计事件，再 ACK，让故障优先表现为可识别的重复，而不是不可恢复的遗漏。

提交成功但 ACK 失败时，消息还可能再次到达，消费者看到已有回执就不再执行相同数据库副作用，只补确认。不需要为了 ACK 失败撤销已提交结果。ACK 只是从该消费组的待确认集合移除消息，不会删除 Stream 实体记录，所以消息保留和存储清理需要另外设计。

### Q038｜XAUTOCLAIM 能证明旧 worker 死了吗？

<summary>查看 / 隐藏参考回答（面试口述版）</summary>

### Q040｜为什么两个消费者不会写两条有效结果？

- [ ] 能解释唯一约束、行锁和事务副作用范围。

- 追问：只写一个“处理过”标记再调用模型是否安全？为什么当前一个回执不能证明外部模型只调用一次？取消与模拟消费竞争时，以什么顺序决定 outcome？
- 证据定位：run 行 FOR UPDATE、DispatchReceipt 主键、test_concurrent_duplicate_consumers；当前有效结果只是回执与审计事件。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

消费者先锁定对应任务行，再检查是否已有消费回执，最后把回执和事件一起提交。同一任务的竞争者会在数据库里串行处理，后到的一方能看到已经完成的回执；回执上的唯一约束进一步限定同一事件只能有一份记录。

模拟消费实验能够保证去重，是因为有效副作用都在同一个数据库事务里。若先记“处理完成”再调用模型，调用失败会漏执行；若先调用模型再记完成，崩溃重试可能重复调用。因此一条回执不等于外部模型恰好调用一次。取消也通过同一任务行竞争，消费者取得锁后根据数据库当前状态决定是否跳过。

</details>

### Q041｜持着数据库锁调用 Redis，有什么代价？

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

发布方案优先控制实现复杂度：relay 锁住一条待发事件，发送后标记完成；另一个 relay 用 SKIP LOCKED 跳过它，处理其他记录。这样不需要额外维护发布领取租约，但网络慢的时候会延长数据库持锁时间，影响连接和吞吐。

所以项目限制单次处理量，配置连接和命令超时，并关闭 Redis 客户端内部重试，交给外层退避处理。但 2 秒 socket 超时不等于整个事务只需 2 秒，还包含连接、数据库等时间。更高吞吐时可以把网络调用移出事务，用有期限的领取记录恢复失联发布者；这会引入新的回收和竞争逻辑，需要实测后再决定。

## 11. 执行权、恢复与沙箱隔离

本主题对应 [执行仓储](../src/spec2repo/storage/execution.py)、[执行器](../src/spec2repo/runtime/executor.py)、[工作区存储](../src/spec2repo/storage/workspaces.py) 与 [Docker 沙箱](../src/spec2repo/sandbox/docker.py)。租约、持有者校验等提问方向参考 S4；快照、取消和故障实验题为项目自拟，不冒称公司原题。

### Q045｜为什么任务领取后还需要租约与独立心跳？

- [ ] 能说明“长任务正常执行”和“worker 已退出”怎样区分。
- 主问题：领取后只记录 worker 名称，为什么不够？怎样选择租约与心跳间隔？
- 追问：模型调用阻塞时心跳怎么办？机器时间不一致怎么办？已经过期但尚未接管，还允许续租吗？
- 证据定位：ExecutionRepository.guard/heartbeat；Heartbeat；长命令心跳测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

Agent 任务可能运行很久，worker 也可能中途退出。如果只记一个负责人，负责人退出后任务会一直被占着。我采用有期限的租约，worker 定期续租，恢复服务负责处理超过有效期的任务。

心跳和执行命令分开运行，避免一次长时间模型调用或工具执行把续租堵住。租约判断统一用数据库时间，续租也要检查当前持有者、执行代次和有效期；已经过期的工作证不能自行续活。租约设置要给正常网络抖动留余量，同时控制故障后的等待时间。我用超过一个租约周期的阻塞命令验证独立心跳，再用真正终止进程的实验验证失去心跳后的接管。

</details>

### Q046｜租约过期了，为什么还需要 fencing token？

- [ ] 能讲出“旧 worker 恢复后迟到提交”的具体竞争。
- 主问题：锁过期并由新 worker 接管之后，旧 worker 为什么仍可能造成问题？
- 追问：只检查 worker 名称行不行？只在领取时检查一次行不行？能保证完全没有重复计算吗？
- 证据定位：Lease、guard，以及旧代次四种提交均失败的测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

租约过期不会自动杀死旧进程。比如旧 worker 暂时卡住，新 worker 接管后它又恢复，如果只依赖锁的到期时间，它仍可能把旧结果写回来。所以每次接管都会递增一个执行代次，相当于给新负责人换一张编号更大的工作证。

提交检查点、更新状态和续租时，都在数据库事务里重新检查代次、持有者和租约，还要确认任务没有进入取消状态。旧工作证即使拿着计算结果回来，也会被拒绝。这保证的是权威结果不会被过期执行覆盖；旧进程可能短暂继续计算，因此文件目录也按代次隔离，不能只保护数据库。

</details>

### Q047｜状态版本与执行代次为什么要分开？

- [ ] 能用“排队、领取、过期、接管”的例子说明两个计数。
- 主问题：已经有乐观并发版本号，为什么又增加 generation？
- 追问：重新排队时是否立刻增加执行代次？恢复通知携带的是哪个代次？
- 证据定位：claim、recover、Run.version/generation、Outbox payload。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

状态版本用于防止并发操作覆盖彼此，例如取消和完成同时发生时，旧状态上的修改不能直接写回。执行代次用于区分不同轮次的执行负责人。重新排队会改变状态，但还没有新的 worker 真正领取，因此这两个数字不能当成同一个含义。

我的做法是状态变化推进版本，每次成功领取推进执行代次。通知记录排队时的版本和代次，worker 先核对通知是否仍对应当前任务，再在同一事务里领取新的执行权。这样既能过滤过时通知，也能在任务接管后拦截旧执行者的迟到提交，日志里还可以看清一次任务经历了多少轮执行。

</details>

### Q048｜XAUTOCLAIM 取到了消息，就能直接重新执行吗？

- [ ] 能区分消息归属与任务执行权。
- 主问题：长任务的通知长时间 pending，另一个消费者接到它后如何处理？
- 追问：原执行者仍在续租时是否 ACK？Redis 消息全部丢失后如何继续恢复？

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

不能直接执行。消息多久没有确认，只反映消息处理进度，不能证明原 worker 已经死亡。Agent 可能正在执行长命令，数据库租约仍然有效。新消费者拿到通知后，要先检查数据库；已有执行者时不启动竞争执行，也不提前确认它正在处理的任务。

执行权的转移由恢复服务完成：发现租约过期后，在同一事务中撤销旧执行权、更新任务状态并写入新的 Outbox。接管者再正常领取。如果 Redis 的消息丢了，数据库对账仍能把待执行任务重新通知出去。这样消息系统负责唤醒，数据库负责决定谁有权执行，两者的故障不会被混为同一件事。

</details>

### Q049｜快照文件与数据库无法一起提交，怎样保证一致性？

- [ ] 能逐个解释快照前、快照后、事务提交后崩溃的后果。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我选择先把快照完整写好，计算并校验内容 hash，再在数据库事务里登记引用和阶段完成事件。因为两个系统不能原子提交，必须选择一个容易处理的失败方向：文件写成功但数据库失败，只会留下未引用文件；如果先写数据库，就可能出现进度显示完成，恢复时却找不到文件。

接管时只认数据库已提交的检查点，先验证快照 hash，再恢复到新的空工作区。旧工作区可能还在被旧进程修改，不能作为可信恢复源。每个执行代次有独立目录，快照存放位置也不挂载给执行容器，因此旧执行者无法通过修改草稿覆盖已保存的恢复点。

</details>

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

取消涉及两件事：先阻止任务继续提交有效结果，再停止实际执行资源。所以运行中的任务先进入取消中，数据库从这一刻开始拒绝后续检查点和完成提交；worker 收到停止信号后移除对应容器，清理成功才确认已经取消。

如果 worker 也退出，恢复服务会接手清理。容器带任务和执行代次标签，清理前核对归属，重复清理没有额外业务效果。取消和完成的竞争由数据库事务决定：完成先提交就保持完成结果，取消先提交就拦截后续完成。这样不会出现接口已经说取消成功，后台却又提交一份成功结果的矛盾。

</details>

### Q051｜为什么允许通用终端，却不用命令黑名单当安全边界？

- [ ] 能说明工具自主性与宿主权限隔离如何同时成立。
- 主问题：agent 可以运行任意命令时，如何限制它的影响范围？
- 追问：为什么不挂载项目根目录或 Docker socket？CPU、内存、进程数各限制什么？
- 证据定位：DockerSandbox.run；容器内权限探针与 HostConfig 断言。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

Coding Agent 需要根据错误反馈选择命令，黑名单很难覆盖脚本、解释器和间接执行。我把限制放到运行环境：非 root、只读根文件系统、只挂载本次工作区、关闭外网，并限制 CPU、内存和进程数量。平台密钥和 Docker 管理接口都不交给生成代码。

这样 agent 可以在授权目录里自主读写和测试，但不能因为选择了某条命令就扩大宿主权限。我用容器内实际探针检查权限、网络和凭证，再检查资源配置、超时清理。普通 Docker 容器仍共享内核；面向更强的不可信多租户场景，可以升级到更强隔离运行时，不能把设置几个参数说成消除了所有风险。

</details>

### Q052｜恢复到检查点，为什么不等于从中断那一行继续？

- [ ] 能界定阶段恢复与进程恢复。
- 主问题：第一阶段提交了，第二阶段做到一半退出，接管者从哪里开始？
- 追问：模型请求可能已经计费怎么办？外部写入操作能直接重放吗？
- 证据定位：execute_fixture、checkpoints、kill 测试的两个检查点代次。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

检查点记录的是已经安全提交的阶段和对应文件状态，不保存进程内存或代码执行位置。第一阶段已经提交、第二阶段中断时，接管者恢复第一阶段的快照，跳过第一阶段，再重新执行第二阶段。阶段划分越细，重复工作越少，但存储和提交成本也越高。

这也意味着未提交阶段可能重复计算。模型请求超时后，供应商可能已经处理并计费；外部写操作也可能已经生效。因此恢复机制不能直接宣称所有副作用只执行一次，需要结合外部接口幂等能力、结果记录和预算限制。项目把阶段提交作为明确恢复边界，优先让中断后的行为可解释、可验证。

</details>

### Q053｜为什么固定镜像，还要锁住依赖和解析 image ID？

- [ ] 能解释运行环境漂移为什么影响验证和恢复。
- 主问题：只写一个镜像 tag 或固定几个主依赖版本够不够？
- 追问：传递依赖变化怎么办？运行中缺少依赖怎么办？固定版本等于永远不用更新吗？
- 证据定位：runtime-image/Dockerfile、requirements.lock、DockerSandbox 初始化。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

恢复和验收需要稳定的环境。如果同一份代码今天能跑、明天因为依赖变化失败，就很难判断是生成质量还是环境漂移。所以基础镜像固定内容摘要，Python 依赖也锁定传递依赖版本，worker 启动时把本地镜像标签解析成不可变 image ID。

运行阶段关闭外网，缺少依赖时作为环境问题处理，不临时下载一个无法复现的版本。环境升级走独立的镜像构建和回归流程，升级后记录新的版本。固定版本的作用是控制变化和支持排查，并不意味着永远不更新，也不代表依赖天然没有安全问题。

</details>

### Q054｜怎样证明故障恢复真的有效，而不是只测了状态变化？

- [ ] 能复述实际 kill、接管、旧写入与取消实验的断言。
- 主问题：你会怎样设计一个能暴露恢复问题的故障实验？
- 追问：为什么要杀独立进程？如何证明没有重跑第一阶段？如何避免无限接管？
- 证据定位：test_killed_worker_restores_last_committed_stage、取消/心跳/恢复上限测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我让任务完成并提交第一阶段，再在第二阶段运行时强制终止独立 worker 进程，等待租约真实到期，然后由新 worker 接管。验证的不只是状态恢复，还包括旧容器被清理、新执行代次增加、第一阶段检查点保持不变，以及第二阶段由新代次提交。

我还修改旧工作区，确认新工作区恢复出的内容不受影响，并直接尝试旧代次提交，确认数据库拒绝。另有长命令续租、运行中取消和容器超时清理实验。恢复次数有上限，持续故障最终进入失败并保留记录，避免一份任务无限消耗资源。这样能分别验证执行权、文件状态和资源清理，而不是看到一个成功状态就认定整条链路可靠。

</details>

### Q055｜你的 Agent 与固定工作流有什么区别？

- [ ] 能区分平台固定边界与模型自主决策。
- 主问题：规划、审批、执行都安排好了，为什么还叫 Agent？
- 追问：模型能自主决定哪些操作？哪些事情必须由平台决定？
- 证据定位：AgentLoop、分阶段工具集合，以及脚本模型的失败反馈集成测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

平台固定的是业务约束和交付流程，比如执行前需要批准、结果需要独立验收、工具只能在隔离目录里运行。实现阶段没有把每个文件怎么生成写成固定步骤，模型会结合规格、当前文件和命令结果，决定下一步是读文件、写代码、执行测试，还是修改计划。

我把自主性放在“如何完成任务”，把权限和成功标准放在平台。这样模型能根据错误反馈改变操作顺序，又不能因为觉得自己做完了，就跳过审批或直接宣布成功。判断是否有 Agent 行为，要看它能不能基于环境反馈选择下一步，而不是看用了多少个模型角色。

</details>

### Q056｜Function calling 返回了合法 JSON，为什么还不能直接执行？

- [ ] 能区分格式合法、业务允许与执行安全。
- 主问题：工具参数通过 schema 后，还要检查什么？
- 追问：模型在规划阶段请求终端怎么办？路径合法是否等于命令安全？
- 证据定位：TOOLS、schemas、工具请求解析、租约校验与 DockerSandbox。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

合法 JSON 只说明数据能解析，schema 校验也只是确认参数结构符合约定。执行前还要确认这个阶段是否允许该工具、任务是否仍有有效执行权，以及操作是否被限制在授权环境里。

例如规划阶段只提供提交计划和提出澄清，模型即使编造终端调用，宿主也会拒绝。批准后可以使用通用终端，但命令在受限容器中运行，不继承平台密钥，也不能选择宿主挂载。这里模型返回的是行动请求，真正的授权和执行由平台完成，不能只靠提示词约束。

</details>

### Q057｜人工审批怎么做到重启后仍然有效？

- [ ] 能说明等待状态、审批对象和恢复调度如何持久化。
- 主问题：用户过了很久才批准，此前处理任务的 worker 已退出，怎样继续？
- 追问：同一审批点两次怎么办？为什么不让 worker 一直等待？
- 证据定位：PlanVersion、decide、enqueue、并发审批与事务回滚测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我把审批当成持久业务状态，而不是一个等待用户回答的内存函数。计划和等待状态写入数据库后，结束这轮执行并释放租约。用户批准时，由 API 在事务里记录决定、切换阶段，并写入新的 Outbox，之后任意 worker 都可以正常领取。

重复批准在同一计划上是幂等的，不会额外产生一次调度。审批决定、阶段变化和 Outbox 一起提交，避免出现“已经批准，但永远没有恢复通知”的情况。这样等待时间不会占用 worker，也不依赖原来的进程仍然存活。

</details>

### Q058｜为什么审批要绑定计划 hash 和规格 hash？

- [ ] 能解释审批后计划或规格变化带来的授权漂移。
- 主问题：只保存一个 approved=true，会有什么问题？
- 追问：用户打开旧页面批准了旧计划怎么办？修改模块目录是否都需要重批？
- 证据定位：ImplementationPlan.fingerprint、ApprovalDecision、decide、内部修订测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

一个布尔值没有说明用户批准了哪份内容。用户看完计划后，计划或规格可能已经变化；如果只检查曾经批准过，执行的内容就可能超出当时的决定。因此我把审批绑定到规格内容、计划内容和修订号，提交决定时核对是否仍然匹配。

内部实现组织可以在原规格下调整，并留下修订版本和原因；涉及业务行为、公开接口或验收条件的变化，要先形成新的规格决定，再重新规划和审批。这样既保留实现灵活性，也能回答“这次执行到底依据哪一次授权”。

</details>

### Q059｜Agent 为什么会无限循环，你怎样限制？

- [ ] 能解释调用前预留预算及恢复后不能重置。
- 主问题：模型不断尝试失败命令，怎样阻止费用和执行时间持续增长？
- 追问：请求发出后 worker 退出，计数怎么办？usage 缺失时写零可以吗？
- 证据定位：reserve、AgentState、循环预算检查与调用前阻断测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

模型可能反复尝试同一个方向，也可能一直输出解释却不完成任务，所以我同时限制调用轮次、上下文规模、输出额度和执行时间。预算在请求发出前就持久化预留，先检查额度，再做外部调用。

这样即使请求已经发送、worker 却在返回前退出，接管者也不会拿到一份全新的预算。未知结果的请求保守保留额度，不自动退款。供应商实际 usage 与预算预留分开记录，缺失时标为未知；费用还需要可靠价格配置，不能把无法计量写成零费用。

</details>

### Q060｜工具执行失败，为什么有时继续、有时立即停止？

- [ ] 能区分开发反馈与平台执行边界失效。
- 主问题：一次 pytest 失败应该直接把整个任务标失败吗？
- 追问：如果是租约丢失、容器故障或超时，还能让模型继续尝试吗？
- 证据定位：CommandFailed、workspace_tool、执行器异常处理与反馈修复测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

要看失败发生在哪一层。测试断言失败、代码语法错误通常是模型需要处理的开发反馈，我会把退出码和截断后的输出返回模型，让它修改代码再验证。如果所有非零退出都终止任务，Agent 就失去了利用反馈调整实现的能力。

但执行权丢失、权限边界失效或容器管理失败属于平台问题，不能让模型靠继续重试解决。平台会停止当前执行，并依据故障类型登记失败或等待恢复。我用实际容器运行一个先失败再修复的测试，确认错误确实进入了下一轮上下文，而不是只看最终文件正确。

</details>

### Q061｜上下文满了，为什么不能随便删消息？

- [ ] 能说明规格、计划与完整工具交互的保留策略。
- 主问题：长期编码任务怎样控制上下文增长？
- 追问：删掉工具调用、只保留工具结果会怎样？如何找回被删掉的文件信息？
- 证据定位：AgentLoop 的上下文裁剪、反馈截断与读取/搜索工具。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

上下文里有不同价值的信息：规格和当前计划决定任务方向，工具输出则可能非常长。我固定保留规格、系统边界和最新计划，对工具反馈限制长度，再按完整的调用与结果对移除旧历史，避免留下无法对应的工具消息。

源码本身存在工作区里，需要时可以重新读取和搜索，不必每轮重复发送整个仓库。这个方案成本较低、行为容易解释，但被裁掉的历史细节可能需要重新查询；更复杂的摘要记忆可以后续加入，同时要防止摘要把错误结论永久保留下来。

</details>

### Q062｜发现规格有歧义，为什么不让模型自己补一个假设？

- [ ] 能区分实现选择与业务决定。
- 主问题：哪些问题应暂停任务，哪些可以由模型自主处理？
- 追问：回答澄清后为什么保存新规格版本？已经批准的计划怎么办？
- 证据定位：request_clarification、clarify、SpecRevision 与旧审批失效测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我会看这个决定是否改变外部可观察行为。目录怎么拆通常是实现选择，可以由模型决定；资源冲突返回什么、是否允许重复创建，会改变业务契约，应当由用户明确。模型提出问题后，平台保存问题并释放执行资源。

用户的回答要落实到完整的新版本规格，而不是只在聊天里补一句话。平台保留旧版本，让新的需求、接口和验收项重新建立关联，再重新规划和审批。这样旧结果仍然能追溯到当时的要求，也不会把旧计划的批准自动扩展到新业务规则。

</details>

### Q063｜模型说完成、开发测试通过，为什么还要独立验收？

- [ ] 能区分实现提交与正式成功。
- 主问题：为什么 finish 工具不能直接将任务改为 SUCCEEDED？
- 追问：如果模型同时写代码和测试，有什么盲区？平台怎样保留后续验收入口？
- 证据定位：finish、WAITING_VERIFICATION、最终快照登记；正式验收在第六阶段实施。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

模型说完成是一个提交信号，它自己写的测试也可能遗漏需求，或者和实现共享同一个错误假设。所以我把生成提交和正式成功分开：先保存不可变产物，随后由平台掌握的独立验收依据判断行为是否满足规格。

开发测试的价值是让模型快速获取反馈，独立验收的价值是固定交付标准。模型可以修改自己的实现和开发测试，但不能修改正式验收规则，也不能通过工具直接把状态改成成功。这样最终结果有独立证据，不依赖模型自我评价。

</details>

### Q064｜怎样记录 Agent 过程，既可排查又不堆满敏感日志？

- [ ] 能说明事件元数据、原始输出与产物分别放在哪里。
- 主问题：出了问题，如何知道是模型调用、工具执行还是审批环节失败？
- 追问：为什么不把完整思考和所有终端输出都写进数据库？hash 能替代原始内容吗？
- 证据定位：agent.call_reserved、model_returned/model_failed、tool_requested/tool_returned 与实验 JSON。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我按一次任务和执行代次串起事件，记录模型调用序号、耗时、用量、工具名和成功标志。工具参数与输出保存摘要 hash，源码作为最终快照保留，这样可以追到哪个环节失败，也能减少数据库里重复堆积大段日志。

hash 用来核对内容身份，不能还原原始输出，所以它不能替代所有调试证据。需要详细复现时，应结合固定规格、产物和有范围控制的实验记录。模型思考、平台凭证和任意终端输出不作为默认持久日志；调用失败只记录受控错误类别或 HTTP 状态，避免把服务响应中的敏感信息直接回显。

</details>

### Q065｜模型自己写的测试都过了，为什么还要独立验收？

- [ ] 能说明实现与开发测试可能共享错误假设。
- 主问题：怎样决定生成项目满足需求，而不是只看模型说完成？

- 证据定位：[HTTP 验收](../src/spec2repo/harness/acceptance_runner.py)、finish 与 SUCCEEDED 分离。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

模型写开发测试能帮助它调试，但如果它把需求理解错，代码和测试可能一起错。我把开发测试和正式验收分开：模型可以改自己的测试，平台根据冻结规格编写独立行为检查。模型提交的是成果快照，只有平台验收通过才能交付。

对 HTTP API，我优先检查接口返回、边界参数、状态转换和重启后的持久化。这些可以用确定性程序判断，不需要再让一个模型猜测是否正确。模型评估可以辅助解释复杂结果，但不能代替已有明确标准的行为验证。

</details>

### Q066｜把验收测试设为只读，为什么还不够？

- [ ] 能解释文件只读与执行隔离的区别。
- 主问题：如何防止生成代码影响评分程序？
- 追问：conftest.py、导入遮蔽和 monkeypatch 有什么风险？两个禁外网容器怎样通信？
- 证据定位：[双容器验收](../src/spec2repo/harness/verification.py)、恶意 conftest.py 集成测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

只读解决的是测试文件不能被直接改写，但如果测试和生成代码在同一个解释器里运行，生成代码仍可能影响导入、插件或断言行为。因此我让应用和验收程序运行在两个容器中，通过 HTTP 观察业务结果，验收进程不导入生成代码，也不运行仓库里的测试插件。

应用容器禁用外部网络，验收容器加入它的隔离网络空间，通过回环地址通信。它们不共享进程空间和工作目录，验收容器不拿平台凭证，也不信任应用输出的“通过”文本。这样评分依据由平台掌握，普通容器的内核隔离边界则单独说明。

</details>

### Q067｜规格或验收程序变化后，原来的通过结果还有效吗？

- 追问：任务修复期间有人放宽验收，会发生什么？没有匹配套件能否算通过？
- 证据定位：SUITES、suite_hash 与 VerificationRepository.commit。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

通过结论只对当时的规格、代码和验收条件成立。我在报告中绑定规格指纹、源码快照、验收套件和镜像身份，使结果可以复查。套件按完整规格指纹注册，只有同名或相同标题不能复用旧验收。

修复过程中套件发生变化，后端会拒绝把不同标准混进同一条验收链。如果确实是验收器有错误，需要说明修订原因、保留旧记录并重新验证。没有匹配套件属于验证条件不满足，不能把零个测试解释成全部通过。

</details>

### Q068｜验收失败后，怎样给模型反馈又避免针对固定样例取巧？

<details>

我把失败整理成验收项、对应需求、期望行为和实际偏差，让模型知道哪条业务规则没有满足。修复从失败版本的快照开始，模型继续自主读代码、修改和测试，平台不会直接告诉它具体该改哪一行。

我还保留冻结输入变体，不把这些具体样例放进修复上下文，减少针对已知输入写特判。隐藏的是样例，不是业务规则，所有检查都必须能从规格推导。有限样例通过提供的是覆盖范围内的行为证据，不能等同于所有输入都绝对正确。

### Q069｜两轮修复上限，怎样保证重启以后不会重新计数？

- [ ] 能解释业务修复、基础设施恢复与模型预算的区别。
- 主问题：修复次数在哪里保存，为什么不能用内存变量？
- 追问：还有修复次数但 token 额度不足怎么办？正常换代次算失败重试吗？
- 证据定位：VerificationRepository.MAX_REPAIRS、报告 repair_scheduled、累计模型预算。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

修复次数依据数据库里已经安排的修复记录累计，验收报告、任务状态和下一条调度通知一起提交。这样进程重启或换 Worker 不会重新获得一份修复额度。最多两轮修复，对应首次验收之后最多再做两次修复和复验。

修复次数和模型预算同时约束执行，哪个先耗尽就先停止。容器管理失败或没有匹配验收套件属于验证错误，不应该让模型反复改业务代码。Worker 失联的接管也有自己的次数统计，不能把正常阶段切换当成故障重试。

</details>

### Q070｜验收结果写入后进程崩溃，修复通知会丢吗？

- [ ] 能从具体失败窗口解释事务与 Outbox。
- 主问题：报告、任务状态和修复入队如何保持一致？
- 追问：旧 Worker 晚到的通过报告能覆盖新结果吗？取消和验收通过同时发生怎么办？
- 证据定位：报告提交事务、注入事件失败回滚测试、过期代次与取消测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

验收完成后，我在一个 MySQL 事务里保存报告、推进任务状态、结束本次执行，并在需要修复时写 Outbox。事务成功以后即使进程退出，Relay 仍能找到调度记录；事务失败时这些变化一起回滚，不会出现报告说要修复、系统却没有留下调度依据的情况。

提交前还会锁定任务并检查租约、执行代次和状态。旧 Worker 的迟到结果不能覆盖新一轮执行；如果取消先提交，后续验收结果也不能把任务改成成功。消息确认发生在这些可靠状态提交之后，重复投递由现有执行权机制处理。

</details>

### Q071｜为什么服务重启后的读取测试很重要？

- [ ] 能区分内存正确与持久化正确。
- 主问题：创建后马上读取成功，是否已经证明使用了持久存储？
- 追问：怎样避免测试拿错数据库文件，或把测试产生的数据交付给用户？
- 证据定位：验收 main/restart 两段、内存 SQLite 反例、原始快照下载。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

创建后立即读取只能证明同一个进程里能找到数据，内存字典也能做到。我让验收器保存创建结果，重启应用进程，然后使用相同数据库文件重新读取并比较，验证数据确实跨进程保留。测试中专门用内存 SQLite 做反例，确认验收器能抓到这种错误。

正式验收从提交快照恢复一个独立副本，并指定新的数据库文件。验收运行产生的数据库不会替换原始交付快照，因此结果可复查，也不会把测试数据混入交付仓库。

</details>

### Q072｜如何区分平台测试通过、生成成功和整体 Agent 效果？

- [ ] 能解释样本、来源与成功率的统计单位。
- 主问题：脚本模型跑通修复，能否说真实模型具有相同修复成功率？
- 追问：同一份快照重复验收两次，算两个生成样本吗？如何控制下载权限？
- 证据定位：真实来源 run、独立报告、脚本模型修复实验与 owner 下载测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我把平台机制和模型效果分开记录。确定性测试证明调度、恢复和修复反馈链路按设计工作；真实模型实验才用于观察生成效果。脚本模型可以稳定制造错误和修复动作，但它不能代表真实模型面对相同错误时一定能修好。

同一份生成快照重复验收只是复查，不增加生成样本数量。报告保留来源任务、模型、快照和验收版本，样本少时只报告逐例结果。正式下载还需要校验 owner、成功验收记录和文件 hash，让交付身份与验收证据一致。

</details>

### Q073｜为什么工具并行不能直接用线程池全部执行？

- [ ] 能解释显式依赖、文件冲突、终端边界和动态参数。
- 主问题：同时写代码、运行测试、提交成果，应该怎样安排？
- 追问：模型漏报依赖怎么办？一个调用需要另一个调用的输出才能决定参数怎么办？

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

工具并行首先要保证执行顺序正确。例如写应用代码和写测试文件可以并行，但运行测试必须等文件写完，提交成果又要等测试成功。我让模型可以显式声明前置调用，同时由平台补充文件读写冲突；终端命令能影响整个工作区，所以作为串行边界。显式依赖只会增加约束，不能绕过平台判断。

执行时只调度前置条件已满足的操作，并限制同时运行的工具数。前置操作失败，依赖它的操作就收到跳过结果，独立分支仍可完成。如果后续参数取决于尚未返回的结果，就需要等下一轮模型决策；依赖图只保证顺序，不会自动理解业务或生成未知参数。

</details>

### Q074｜并行工具会怎样影响上下文、容器和故障恢复？

- [ ] 能说明结果配对、整组裁剪、容器生命周期和部分成功。
- 主问题：多个工具完成顺序不同，如何保证下一轮模型拿到有效上下文？
- 追问：一个工具结束时如何避免清理其他工具？某个工具失败是否回滚所有写入？

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我把一次模型响应和它的全部工具结果作为一个完整交互。工具可以乱序完成，但返回模型时按原始调用顺序组织，并用调用 ID 配对；上下文裁剪也整组删除，避免模型看到缺失的工具回复。被依赖条件阻止的调用同样要有结果，让模型知道它没有执行。

容器方面，每个并行工具使用唯一名称，仍保留任务和执行代次标签。正常完成只清理自己的容器，取消和恢复则清理该代次所有容器。每个工具仍需通过租约校验。多个文件操作没有跨工具事务，一个失败时另一个可能已经成功，因此系统保留反馈，由模型修复；最终只有通过快照提交和独立验收的成果才能交付。

</details>

### Q075｜Agent 项目的吞吐应该怎么测？

- [ ] 能区分接入吞吐、有效交付吞吐、成功率和测试环境。
- 主问题：任务接口每秒接受一百多个请求，是否代表每秒完成一百多个 Agent 任务？
- 追问：失败很快会不会让数字更好看？少量样本能否说明最佳 Worker 数量？

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我把接入层和执行层分开测。接入层统计 HTTP 请求完成事务落库的速度和尾延迟；执行层统计从提交到独立验收结束的耗时，并用验收通过的任务数计算有效吞吐。失败任务不能算作交付，所以吞吐必须和成功率一起报告。

对照实验保持任务规格、模型、预算和验收标准一致，同时记录工具并行情况、模型调用与用量，以及失败原因。少量批次只能帮助发现问题，不能证明稳定容量；要判断最佳 Worker 数，还需要持续负载、多次重复和资源监控。测试库使用内存文件系统等条件也必须交代，避免把本机数字包装成生产能力。

</details>

## 12A. 任务记忆与上下文治理

### Q076｜上下文和记忆有什么区别，为什么不保留全部聊天记录？

- [ ] 能说明单次上下文、任务记忆和累计预算的区别。
- 追问：压缩后还能知道什么？它会退回已经花掉的 token 吗？
- 证据定位：AgentLoop 的上下文组装与 context_compacted 事件。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

上下文是这一轮实际发给模型的材料，任务记忆是之后还值得取用的信息。编码任务的日志和读文件结果会不断增长，全部保留既占预算，也容易让模型忽略关键问题。我把规格和计划固定保留，把进展、决策、失败尝试整理成结构化笔记，工具结果只放简短预览，需要细节时再按证据编号读取。

</details>

### Q077｜模型记错了怎么办，如何防止记忆变成错误事实？

- [ ] 能区分模型陈述、工具观察和独立验收结论。
- 追问：某次 pytest 成功，是否代表现在的代码仍然正确？
- 证据定位：model_notes、observations、failures 与独立 Verification。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我没有把模型笔记当作事实数据库。模型可以记录为什么选择 SQLite、下一步修什么，但这些只是工作假设。工具观察由平台产生，说明某次命令的退出结果，并提供输出证据。最终是否完成需求，由独立验收决定。

这三层的可信程度和用途不同。即使测试曾经通过，后面改过代码也需要重新验证；即使笔记写着完成，也不能直接推动任务变成成功。规格和权限来自平台规则，记忆只能帮助模型决策，不能改变业务约束或扩大工具权限。

</details>

### Q078｜为什么记忆恢复要和代码快照绑定？

- [ ] 能用崩溃时序说明“记忆超前于代码”的问题。
- 追问：旧 Worker 回来继续写怎么办？只持久化聊天记录够吗？
- 证据定位：finish 事务、task_memories、恢复专项测试。

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

假设模型已经写完一个文件并记下完成，但提交前进程崩溃，系统恢复的是上一次代码快照。如果把最新笔记直接带回来，模型就会误以为那个文件已经存在，跳过必要工作。所以我把记忆和提交快照关联，新执行只加载同一任务、同一规格、同一快照的记忆。

提交时记忆关联和任务状态变更在同一个数据库事务中完成；写入还要检查租约和执行代次，旧 Worker 失去执行权以后不能污染新状态。更细粒度恢复需要同时保存文件状态，不能只保存更多聊天记录。

</details>

### Q079｜长工具输出怎么处理，按证据 ID 读取如何隔离？

- 追问：分页读取成功是否代表原命令成功？保存的是完整日志吗？

我把有界工具输出存到独立表里，模型先看到头尾预览和证据编号。错误细节不够时，它可以主动分页读取，这样不需要每一轮都重复发送长日志。取回结果会保留原命令的成功状态和退出码，避免把读取成功误解为命令成功。

证据编号不是访问凭证。读取仍要验证任务、规格和执行代次；跨代次只允许读取匹配快照引用的证据。存储有单条和每任务总额度，并在任务锁下检查，避免并行写入突破上限。沙箱本身有日志捕获上限，所以接口会明确标记这是有界捕获，不能声称保存了完整日志。

### Q080｜如何证明上下文改造有效，而不是加了两个工具？

我把验证分成两层。工程层强制触发裁剪和执行权丢失，检查关键笔记、失败证据、分页取回和快照一致性，确保系统不会串任务或恢复错误状态。模型效果则用相同规格、模型和预算做对照，并重复多次，比较验收成功率、重复读写次数、失败后重复尝试次数和实际 token 使用量。

单纯 token 下降不能证明效果变好，因为也可能是提前失败了。因此要同时看成功交付和成本。脚本测试可以证明机制按设计运行，但不能代替真实模型效果评估，也不能从一次成功就推断长任务能力提升。

</details>

### Q081｜为什么做了验收，还需要 Agent 评估？

- 追问：模型换了版本，怎样判断值得升级？

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

验收判断某次生成的代码是否满足需求，评估判断整个 Agent 在一组任务上表现如何。一次通过不能说明系统稳定，也不能说明新提示词优于旧提示词。我用固定任务、相同预算和环境，对不同策略重复运行，同时看最终成功率、修复率和交付成本。这样升级模型或调整上下文时，就能依据结果决定是否采用，而不是只看几次演示。

</details>

### Q082｜怎样识别无效循环，同时不误伤正常测试重试？

- [ ] 能说明输入、输出、文件变化和跨轮次四个条件。
- 追问：模型连续运行三次 pytest 就该停止吗？

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

不能只看命令重复。改完代码再跑同一个测试是正常过程，所以我结合参数、捕获输出和工作区内容指纹判断。只有跨多个模型轮次得到相同结果、代码也没有变化，才提醒模型检查证据并换一种思路。提醒后相同终端失败继续发生，才受控停止；重复读取只提醒。无法可靠读取工作区时，检测器不把未知状态当作没有进展。这是保守启发式，最终仍由独立验收判断成果是否正确。

</details>

### Q083｜Trace 相比普通日志多解决了什么？

- [ ] 能沿一次失败关联模型调用、工具证据和验收。
- 追问：为什么不能只用模型返回的工具调用 ID 关联所有记录？

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

普通日志告诉我发生过什么，关联轨迹让我知道某次验收失败之前，模型做了哪些调用、工具返回了什么、是否发生上下文裁剪或重复尝试。我使用任务、执行代次、模型轮次和工具调用 ID 共同关联，再通过证据编号取回有界输出。这样可以区分模型协议问题、工具执行问题和成果不满足需求。工具 ID 可能跨轮次重复，单独使用它会串记录；轨迹也不需要保存模型私有推理文本。

</details>

### Q084｜Agent 的 token 成本应该怎样统计？

- [ ] 能解释为什么不能只统计成功样本。
- 追问：部分调用没有 usage 时怎么报告？

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我会把失败任务消耗也算进交付成本，用全部任务的实际 token 总量除以成功交付数。只统计成功任务会隐藏失败浪费，可能让成功率很低的方案看起来很便宜。没有 usage 的调用不能当零消耗，因此我单独报告已知 token 和覆盖率，信息不完整时不给完整平均值。预算预留是执行前的保守限制，也不能当作供应商实际计费量。

</details>

### Q085｜如何避免评测对照不公平和只对固定样例有效？

- [ ] 能说明控制变量、策略顺序、重复试验与保留集。
- 追问：两个策略完成的任务数量不一样，能直接比较成功率吗？

<details>
<summary>查看 / 隐藏参考回答（面试口述版）</summary>

我先固定规格、验收器、模型、预算和环境，再比较策略，并保存代码和输入指纹，避免运行中悄悄改变条件。策略顺序轮换，保留逐例结果和失败原因，基础设施中断的部分报告不能当成完整对照。调优任务和最终保留任务也应分开，避免反复针对同一份反馈写特判。小样本结果适合发现问题，不能直接推出统计显著或跨场景泛化，真实提升要由重复试验和独立任务支撑。

</details>

## 14. 维护规则

每完成一个改造阶段，同步更新本文件，作为阶段交付的一部分。当前请求不创建定时任务，更新发生在后续项目实施过程中。

1. 下一阶段从 Q086 起追加稳定题号，按主题放置；不要因重排章节改变旧题号。
2. 优先新增当阶段真实涉及的 5～10 道核心题，必要时把新追问加入已有题，避免同义重复。
3. 每题写清主问题、追问、证据定位；外部面经改写须标来源，项目自拟题不要冒称公司原题。
4. 后续阶段再次核验相关面经，并用官方文档和实际测试核验技术结论，不照搬面经答案。
5. 能力状态发生变化时更新旧题的边界说明。例如 MySQL 并发测试完成后，为 Q003 追加数据库实验证据。
6. 用户回答后再记录掌握情况；代码或测试通过不自动勾选。误解写入复盘记录，并标待复习。
7. 保持同一份题单作为题目来源；各阶段学习文档链接到对应题号，不再维护重复问题列表。
8. 新增题目时同步补充默认折叠的口述答案，统一采用项目完成后的面试场景，直接讲问题、方案、关键机制和技术取舍，不使用“当前只完成了”“还未实现”等阶段性话术。实际开发进度放在证据定位和阶段学习记录中；实验数字与个人经历保持可核对。
