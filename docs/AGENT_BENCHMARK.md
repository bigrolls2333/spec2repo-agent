# 真实 Agent 并发实验

2026-10-23 的最新实验使用 1/4/16 并行任务及双倍预算，**21 个任务成功 14 个（66.7%）**；16 并行组成功 **11/16（68.75%）**，有效吞吐 **4.74 任务/分钟**。下文保留首轮 3/7、依赖调度后第二轮 6/7 的完整记录，避免只选择最好结果。各轮均为小样本实验，不是持续稳定吞吐基准。

## 测量范围

从创建任务开始计时，经过 MySQL 事务、Outbox Relay、共享 Redis Stream 消费组、Agent 规划、自动批准示例计划、模型自主编码与 Docker 工具执行，再进入独立验收及预算内修复流程。只有状态为 SUCCEEDED 且最终验收报告为 PASSED 才计入成功交付；失败和待澄清任务不算产出。

每组 N 个任务配 N 个 AgentWorker 工作线程，共享一个真实 Redis 消费组和 SQLAlchemy 连接池。API 提交和审批通过进程内 TestClient 完成；因此它测量真实 Agent 工作链路，不包含外部 HTTP 接入网络耗时，也不是多机器部署实验。自动审批只针对实验身份，排除人工等待；生产审批接口和约束没有修改。

每组从第一个任务提交前开始计时，到所有任务被轮询观察为结束为止。状态轮询间隔约 200 ms。有效吞吐 = 验收通过任务数 / 该组总耗时 × 60。时间包含调度与验收，排除预先部署镜像、数据库启动及结束后的清理。每组只投放一批任务，没有持续补充任务维持饱和，因此不能将批次吞吐直接解释成长期容量。

## 环境和预算

| 项目 | 配置 |

| 模型 / 服务 | deepseek-flash / api.deepseek.com |

| 并发档位 | 1、2、4，每档一组，共 7 个任务 |

| Docker | 29.5.3；daemon 可见 16 CPU、16,682,475,520 字节内存 |
| 数据库 | 专用 MySQL 8.4.11 测试库；数据目录使用 tmpfs |
| 队列 | Redis 7.4，随机实验专用 Stream 和 execution-v1 消费组 |
| 执行方式 | 同进程多 Worker 线程，独立心跳，真实 Docker 工具容器和验收容器 |
| 单任务预算 | 最多 32 次预留、240,000 保守 token 额度、1,800 秒预留时间 |
| 预算计算 | 每次预留请求 UTF-8 字节数 + 4,096，以及 150 秒；不是实际 token 计费值 |
| 限制 | 每任务最多 2 轮验收修复；每组观察期限 900 秒；不自动重跑失败任务 |

受每次预留 150 秒的约束，单任务实际最多能预留 12 次调用，也可能先触发 token 额度限制。实验未调整这些参数，未更改模型提示词、工具协议或验收标准。

镜像固定为 `sha256:4258424cb9f118daaa16964e0d5bf0bf6c1ef7bfad32c744983b87840242b16d`，与已有生成实验使用同一镜像。

## 失败分析与消耗

三个失败任务在 provider 返回多个 tool_calls 后触发 `Only one tool call per turn is allowed`。平台已经发送 `parallel_tool_calls=false`，但适配器仍需校验实际响应；本实验表明仅设置该参数不能确保每次响应都遵守单工具协议。审计事件记录了拒绝原因，任务没有被误报为成功。

另一个任务在 11 次调用后累计预留 236,679 / 240,000，剩余 3,321 不足以预留下次调用，因而触发 BudgetExceeded。这是保守预留额度耗尽，不表示真实计费 token 已用到 240,000，也不是任务实际运行了 1,650 秒。

七项任务合计预留 52 次调用，其中 49 次响应通过适配器并记录 usage：输入 213,296、输出 25,125，总计 **238,421 个 provider 报告 token**。其余 3 次协议拒绝的响应没有进入 usage 记录，因此这个总数只是已记录用量，不能当作完整账单。没有价格配置，费用为未知，没有估算人民币金额。

建议下一轮先验证两个改进方向：

1. 对多工具响应进行有界协议纠正，或明确支持逐项校验后串行执行。需要保持每个工具调用和结果配对、所有权检查、预算约束以及 finish 等终止工具的顺序语义，不能只取第一项并静默丢弃剩余调用。
2. 分析保守预留和真实 usage 的差异，给提交及修复保留可用额度，并检验上下文裁剪效果。任何预算策略调整都应独立对照验证，避免为了成功率直接取消上限。

本轮没有修改上述生产逻辑。7 个样本不足以确定最佳 Worker 数，更不证明 128 个 Agent 可同时稳定运行。接口接入压测结果另见 [API_BENCHMARK.md](API_BENCHMARK.md)。

## 复现与证据

脚本：[benchmark_agent.py](../scripts/benchmark_agent.py)。首次执行在单任务全失败后停止，检查失败原因后，仅运行剩余 2、4 并行组；没有重跑或剔除失败样本，实际仍为 7 个任务。脚本现保留业务失败结果并继续后续档位，只在编排或清理异常时停止。

- [单任务原始报告](experiments/agent-benchmark-66f9fc6dcf2f43798d228f9ad0e3e8c3.json)
- [2、4 并行组原始报告](experiments/agent-benchmark-48fbacfe72fd496f9adffe46ff0eaf1d.json)

报告包含每个任务的模型事件、预算、快照指纹和独立验收报告；工作区与快照保存在被忽略的 `.runtime/agent-benchmark/` 目录。脚本不把模型密钥保存到报告。

在已有测试环境配置、运行镜像和模型凭证的前提下，从 spec2repo 目录执行以下命令会发起新的付费模型实验，不是重放已有结果：

```powershell
docker compose --env-file .env.test -f compose.test.yaml up -d --wait
.venv/Scripts/python.exe scripts/benchmark_agent.py --model-env ../paper2repo_agent/.env
docker compose --env-file .env.test -f compose.test.yaml stop
```

首轮实际使用默认参数启动首组，再通过 `--concurrency 2 4` 完成剩余授权任务。不要与清理测试库的完整测试套件同时运行。每次重新运行都会产生新的模型费用；脚本默认仍为 7 个任务，显式参数允许最多 21 个任务、最高 16 个 Worker，不是跨多次运行的账户消费上限。

用户授权扩大实验后，使用如下命令执行 1/4/16 档位和双倍任务预算：

```powershell
.venv/Scripts/python.exe scripts/benchmark_agent.py --model-env ../paper2repo_agent/.env --concurrency 1 4 16 --budget-multiplier 2 --max-output-tokens 8192
```

预算覆盖只作用于该实验进程，默认生产实现没有提高上限。脚本限制同时获准运行的工作区工具为 16 个，等待槽位期间继续检查所有权；独立验收容器不占这些槽位，因此不能把 16 解释成包含验收在内的所有容器总上限。报告记录 `peak_tool_slots`，它表示同时获准进入工具执行流程的数量，不是通过 Docker 采样得到的精确运行中容器数。

## 第二轮：依赖调度后的同预算对照

实现见 [并行工具设计](PARALLEL_TOOLS.md)。本轮仍执行 1、2、4 并行任务各一组，共 7 个，保持原任务预算上限、4,096 输出额度、模型、规格和验收套件不变。工具参数新增依赖字段，提示词和模型请求启用多工具，因此它是整体实现前后对照，不是只改变线程数的微基准。

| 并行任务数 | 成功 / 总数 | 成功率 | 批次耗时 | 有效吞吐 |
|---:|---:|---:|---:|---:|
| 1 | 0 / 1 | 0% | 21.23 s | 0 任务/分钟 |
| 2 | 2 / 2 | 100% | 65.62 s | 1.83 任务/分钟 |
| 4 | 4 / 4 | 100% | 75.95 s | 3.16 任务/分钟 |

原始证据：[第二轮完整报告](experiments/agent-benchmark-6d59a69334b54a25be0487d0e430211e.json)。六项成功均首次通过正式验收；审计记录包含 14 轮大于 1 的工具并行，单轮最高 4。59 次模型调用记录输入 279,718、输出 44,521、合计 324,239 token。未配置价格，费用未知。

唯一失败的单任务在第二次响应后触发 ModelError，响应输出恰好用满 4,096 token，但现有记录没有保存 finish_reason 或完整失败参数，因此只能把输出截断列为疑似原因，不能证明具体是哪一个参数不合法。没有重跑该失败样本。

4 并行组观测有效吞吐从 2.24 升至 3.16 任务/分钟，但该组总耗时也从 53.52 升至 75.95 秒。提升来自该小样本组成功交付数增加，不能宣称单任务延迟降低，也不能将一次比较解读为统计显著的性能提升。

完整回归：133 passed、2 skipped，包含新增真实容器并行写入、终端检查和快照测试。首次回归受 Windows 旧 pytest 临时目录权限影响，改为工作区内全新临时目录后运行通过；同时更新了适配器测试中原单工具协议的预期。

## 第三轮：1/4/16 Worker 与扩大预算

用户明确授权 21 个新任务，并允许增加预算。每任务上限调整为 64 次调用、480,000 保守 token 额度、3,600 秒预留时间，单次输出额度为 8,192。全局工作区工具槽位为 16，每个 Agent 同轮最多 4 个工具；审批、规格和正式验收套件保持一致。

原始证据：[第三轮完整报告](experiments/agent-benchmark-3d49a844295b48cb8fafe7c306b109a6.json)。本轮没有失败后重新抽样，也没有在运行过程中修改实现。

| 并行任务 / Worker 数 | 成功 / 总数 | 成功率 | 批次耗时 | 有效吞吐 | 成功任务耗时中位数 | 工具槽位峰值 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1 / 1 | 100% | 63.10 s | 0.95 任务/分钟 | 62.90 s | 4 |
| 4 | 2 / 4 | 50% | 120.00 s | 1.00 任务/分钟 | 59.16 s | 9 |
| 16 | 11 / 16 | 68.75% | 139.21 s | 4.74 任务/分钟 | 103.10 s | 16 |

成功的 14 个任务各自首次通过 15 项独立验收，合计 210 项检查；本轮没有正式验收后的修复调用。16 并行组最慢成功任务为 130.07 秒。7 个失败任务全部保留，其中 6 个记录为 ModelError、1 个为 BudgetExceeded。6 个 ModelError 都发生在模型响应已经返回并记录 usage 之后，未出现适配器 `agent.model_failed` 事件，说明不是前一轮的“多工具直接拒绝”或已记录的网络错误；但现有报告未保存批次校验细分原因，不能把它们全部归因为某一种依赖、参数或输出截断错误。

193 次模型调用均记录了 usage：输入 **946,725**、输出 **140,865**、合计 **1,087,590 token**。价格未配置，费用未知。审计记录共 42 轮工具并行，单轮最多 4 个；没有编排中止或清理错误。

扩大预算没有保证每组成功率提高。4 并行组有两个任务运行较久后失败，尽管两个成功任务约 55～63 秒交付，批次吞吐仍必须把失败任务占用的时间纳入分母。16 并行组的有效吞吐更高，但成功任务的中位耗时也上升；没有资源剖析和重复样本，不能断言最佳并发度或把变化归因于唯一组件。

下一步适合增加可恢复的批次校验反馈和脱敏错误分类，例如参数 schema、依赖引用或控制操作位置，而不是直接继续增加并发。记录 provider 的 finish_reason 也有助于区分输出截断与格式错误。上述方向是后续工作，本轮不通过修改失败标准提高成功率。
